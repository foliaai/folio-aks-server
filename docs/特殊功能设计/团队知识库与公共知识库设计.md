# 团队知识库与公共知识库 — 技术设计文档

> 涉及仓库：`folio-aks-server`（主战场：team 层 + 判权 + 检索链路）、`folio-auth-server`（两个只读查询 API）、`folio-web`（分区 UI + 团队管理面）
> 相关模块：`api/routers/knowledge/`、`src/db/mysql/models/business/`、`src/retrieve/`、`src/service/chat/`、auth `app/repos/organization_repo.py`
> 定稿日期：2026-10-16（设计定稿，**未实施**）
> 配套背景：组织模型见 `folio-auth-server/scripts/mysql/schema.sql`；对话链路见本目录《知识库对话设计.md》

## 1. 背景与目标

当前知识库是**个人库单 owner 模型**：`knowledge_base.user_id` 是唯一归属字段，向量层隔离也靠 `user_id` 过滤实现。本设计引入两类新的可见性：

| 类型 | 语义 |
|---|---|
| **团队知识库**（team） | 绑定一个独立"团队"，团队成员读写同权，知识沉淀随团队存续 |
| **公共知识库**（public） | 所有登录用户可读；写入收敛到创建者/管理员 |

两套部署环境（JP 内网 = OA 登录 + 组织数据齐全；prd 公网 = Logto 登录 + 无任何组织数据）**共用同一套判权代码、零环境分支**，差异全部收敛到"团队的初始成员从哪来"（JP：从 OA 部门一键导入快照；prd：手工邀请）。

### 1.1 设计目标

1. 个人库（private）行为**零变化**，存量数据不迁移（默认值即 private）。
2. 判权逻辑单一实现，JP / prd / dev 三环境同一份代码。
3. 授权客体是**独立 team 层**，不依赖 OA 组织结构，不受 OA 同步语义影响。
4. 检索 / 对话 / 文件 / 引用全链路权限一致，不留"共享面放大越权"的口子。

### 1.2 非目标（本期不做）

- 组织层级树（`organization` 表保持扁平，仅作展示与导入源）。
- 团队内细粒度角色（只分 owner / member）。
- owner 转让（平台 admin 兜底）。
- 跨库混合检索（Milvus filter 的 OR 组合），见 §10 遗留项。
- 知识库成员级 ACL（只有"团队全员"一档）。

## 2. 现状盘点（设计依据，含代码事实）

### 2.1 归属模型：user_id 贯穿全链

| 层 | 现状 | 位置 |
|---|---|---|
| KB 表 | `user_id` 唯一归属字段 | `src/db/mysql/models/business/knowledge_base.py:44-48` |
| 文件表 | 联合主键 `(user_id, file_id)`，索引 `idx_user_kb(user_id, knowledge_base_id)` | `src/db/mysql/models/business/workspace_file_system.py:36,43-54` |
| chunk/section 关系表 | 只有 `KnowledgeMixin` 的 kb 维度冗余列，**无 user_id** | `src/db/mysql/models/base/chunk_section_document.py:20-59` |
| Milvus 向量 | schema 含 `user_id` + kb 字段，写入时带 | `src/db/milvus/models/base/chunk_schema.py:95-125`、`src/db/kafka/writers/embedding_milvus_writer.py:327,350` |
| 会话表 | `user_id` + JSON `knowledge_base_ids` | `src/db/mysql/models/conversation/chat_session.py` |

### 2.2 检索隔离的真实实现方式

**不校验 KB 归属**，靠 `MetadataFilter(user_id)` 拼进 Milvus 过滤表达式（`src/retrieve/types/query.py:42-65`，`user_id` 与 `knowledge_base_id` 逐字段 AND）。

用一个例子说明它为什么天然挡住团队库（这是本次改造最深的一处动机）：

> 张三（OA 工号 84852241）往团队库 `kb-team01` 传了文档，向量写入时带 `user_id="84852241"`。
> 李四检索这个库时，Milvus filter 是 `user_id == "李四" AND knowledge_base_id == "kb-team01"` —— 命中 0 条。
> **团队库的数据全是别人 user_id 写的，现有过滤逻辑查不到。**

字面检索路（Mongo → `ChunkSectionDocument` 回查 MySQL）本来就按 kb/doc/section 解析、无 user_id 条件（`src/retrieve/capabilities/lexical/_filter_helper.py:30-108`），天然兼容共享库。

### 2.3 内容级共享底座已存在（利好）

`workspace_file_system` 的 SHA256 去重是**全局**的：`get_by_sha256` 无 user 条件（`src/db/mysql/repositories/business/workspace_file_system_repo.py:267-285`），不同用户上传同内容文件共享同一 `document_id` 与向量。删除互不影响靠墓碑按 `(user_id, kb_id)` 排除（`src/service/knowledge/tombstone.py:79-93`）。也就是说"共享正文 + 各自 file 记录"的多租户语义**今天已经在跑**，团队库只是把共享面从"同内容的不同用户"扩大到"同团队"。

### 2.4 现存三个越权洞（团队库上线前必须先修）

单 owner 时代这些洞只泄露个人数据，共享库一上线影响面直接变大：

| # | 洞 | 位置 | 现状 |
|---|---|---|---|
| H1 | `POST /api/knowledge/retrieve/single` 不传 user_id，任何登录用户可按 kb/document 直调原子检索能力 | `api/routers/knowledge/retrieve.py:172-199`、`src/service/knowledge/retrieve_service.py:231-236` | 只鉴登录 |
| H2 | chunk 三端点（image-preview / raw-image / position）只鉴登录不鉴归属，路由的 `_user_id` 参数被直接弃用 | `api/routers/knowledge/chunk.py:41,125,229` | 只鉴登录 |
| H3 | `create_session` 对 `knowledge_base_ids` 不校验归属，可把别人的 kb_id 塞进会话 | `src/service/chat/session_service.py:82-161`（对比 folder 有校验 `:126-131`） | 无校验，靠 Milvus user_id filter 兜底 —— 检索链路改共享模型后这层兜底消失，**必须前置补上** |

### 2.5 存量 bug（顺手记录，不强制本期修）

- 会话绑定多 KB 时，检索工具只取第一个：`kit.knowledge_base_ids[0]`（`src/service/chat/tools/handlers/search_knowledge_base.py:154-159`、`grep_chunks.py:109-117`）。前端目前恒传单元素（`lib/api/chat.ts:87-94`），暂未暴露。

### 2.6 auth 侧组织数据现状

- `organization`（`department_id` INT 主键 = OA DepartmentID，扁平、name 存 `IT技术中心/IT研发部` 全路径仅展示、`source` 预留 `oa`/`manual`）+ `user_organization`（`(user_id, department_id)` 联合主键、`is_main`、`idx_uo_department` 反查索引）。
  - `folio-auth-server/app/models/organization.py:27-60`、`app/models/user_organization.py:23-49`
- 唯一写入路径：OA 登录时 `sync_user_departments` **整体替换**该用户的全部 `user_organization` 行（先 delete 再 insert，`app/repos/organization_repo.py:70-81`）。→ **在 `user_organization` 上混 OA 数据与手工数据不可行**，手工加的部门会被下次登录冲掉，这是"独立 team 层"的直接技术动因。
- Logto 登录路径（prd 用）完全不触碰这两张表 → **prd 恒为空表**（`app/routers/auth/logto.py:45-64`）。
- JWT 只有 `sub/iss/iat/exp/role/name`，不带组织（`app/services/token_service.py:31-63`，默认 7 天有效）。
- 组织查询 API 只有"用户 → 部门"（`GET /api/user/profile` 的 `departments`，`app/routers/user.py:58-70`）；**没有**"部门 → 成员"和用户搜索。

## 3. 总体设计

### 3.1 权限模型

```
knowledge_base.visibility ∈ { private(默认), team, public }
knowledge_base.team_id     -- visibility=team 时绑定的团队

判权（AKS 本地一条 SQL 查 team_member）：
  private : user_id == KB.user_id                          → 读/写/管理
  team    : user ∈ team_member(team_id)                    → 读/写
            team owner（role='owner'）/ KB 创建者 / 平台 admin → 管理
  public  : 任何登录用户                                    → 读
            KB 创建者 / 平台 admin                          → 写/管理
```

- **团队成员读写同权**（含上传、删除文档——删除按 kb 维度墓碑对全团队生效）。
- 平台 admin 复用 `folio-auth-core` 的 `require_admin` 判定（role claim 或 `FOLIO_AUTH_ADMIN_USER_IDS` 白名单，`folio-auth-core/src/auth_core/deps.py:217-238`），AKS 侧只需配 env。
- 公共库创建权由 env 开关 `PUBLIC_KB_ADMIN_ONLY` 控制：**prd 建议 true（公网广播面），JP false**。

### 3.2 授权客体：独立 team 层（关键决策）

**不绑 `department_id`，不碰 `user_organization`**，新建 `team` / `team_member` 两表（放 AKS 库，见 §3.3）：

```
JP：建团队 →（可选）一键从我的 OA 部门导入成员快照 → 此后独立维护
prd：建团队 → 手工逐个邀请（搜人）
```

推翻过的两个备选方案及原因（决策记录）：

| 备选 | 否决原因 |
|---|---|
| KB 绑 `department_id`（严格按 OA） | ① `user_organization` 整体替换语义导致无法手工增删成员（§2.6）；② 组织粒度与协作单元错位、跨部门项目无法建库；③ prd 仍需另做"手工组织"管理面，两环境模型分叉 |
| 复用 `knowledge_type` 字段 | 那是内容类型（`common_file`），与归属语义正交，混用会缠死 |

由此带来的额外收益：**prd 原计划的手工组织管理 CRUD 整个不用做了**。`organization` 表回归本职——JP 侧 OA 同步镜像（个人资料卡展示 + 团队导入数据源），prd 继续空着，auth 库**零 DDL**。

### 3.3 team 层放 AKS 而非 auth-server（关键决策）

| 理由 | 说明 |
|---|---|
| 热路径 | 判权发生在每个知识库请求上，本地索引查询比跨服务调 auth API 快且无缓存失效问题 |
| 域归属 | auth-server 保持纯身份域；team 当前唯一消费方是 AKS（agent-server 刻意不持有越权能力，见 §7.4） |
| 解耦 | JP 的"从部门导入"是纯前端编排：先调 auth 拿部门成员（§6.1 新 API），再把 user_id 列表传给 AKS 建团队接口，两服务互不感知 |

### 3.4 环境差异全景（最终剩余差异很短）

| 差异点 | JP（内网 OA） | prd（公网 Logto） |
|---|---|---|
| 团队初始成员来源 | 一键从 OA 部门导入快照 | 手工逐个邀请 |
| "从部门导入"入口 | 有（数据驱动：`profile.departments` 非空才显示，与组织信息卡同款模式 `components/layout/ProfilePanel.tsx:197-216`） | 自然不出现 |
| 公共库创建权（`PUBLIC_KB_ADMIN_ONLY`） | false（创建者即可维护） | **true（仅 admin 可建）**，防任意用户向全体注册用户广播内容 |
| 其余一切 | 同一份代码：team CRUD、成员管理、KB 绑定、判权、检索链路、前端团队库 UI | 同左 |

## 4. 数据模型设计

### 4.1 DDL

```sql
-- ============ 1) 现有表变更（三环境手工 ALTER，create_all 不会补列！） ============
ALTER TABLE knowledge_base
  ADD COLUMN visibility VARCHAR(16) NOT NULL DEFAULT 'private'
    COMMENT '可见性：private=个人（默认，存量数据零迁移）/ team=团队 / public=公共',
  ADD COLUMN team_id VARCHAR(64) NULL
    COMMENT 'visibility=team 时绑定的团队ID，其余为 NULL',
  ADD INDEX idx_visibility (visibility),
  ADD INDEX idx_team (team_id);

-- 文件表补 kb 前导索引（现有 idx_user_kb 是 user_id 前导，团队库按 kb 聚合查询用不上）
ALTER TABLE workspace_file_system
  ADD INDEX idx_kb (knowledge_base_id);

-- ============ 2) 新表（Base.metadata.create_all 自动建，此处为等价 DDL） ============
CREATE TABLE team (
  team_id      VARCHAR(64)  PRIMARY KEY COMMENT '团队ID（team-{uuid}）',
  name         VARCHAR(255) NOT NULL COMMENT '团队名',
  description  TEXT         NULL,
  -- owner 不在表上冗余，由 team_member.role='owner' 表达（一人一档，避免双写不一致）
  status       VARCHAR(16)  NOT NULL DEFAULT 'active',
  creator      VARCHAR(64)  NULL,
  create_time  DATETIME     NULL,
  updater      VARCHAR(64)  NULL,
  update_time  DATETIME     NULL,
  deleted      INT          NOT NULL DEFAULT 0
) COMMENT '团队（授权客体，独立于 OA 组织）';

CREATE TABLE team_member (
  team_id     VARCHAR(64) NOT NULL COMMENT '→ team.team_id',
  user_id     VARCHAR(64) NOT NULL COMMENT '→ auth user_profile.user_id（OA 工号 / Logto sub）',
  role        VARCHAR(16) NOT NULL DEFAULT 'member' COMMENT 'owner=创建者 / member=成员',
  joined_time DATETIME    NULL,
  PRIMARY KEY (team_id, user_id),
  INDEX idx_tm_user (user_id)   -- 支撑"我加入的团队"反查
) COMMENT '团队成员（快照语义：导入后不受 OA 同步影响）';
```

ORM 落点：`src/db/mysql/models/business/team.py`、`team_member.py`（沿用 `KnowledgeBase` 的 BaseModel 风格）；Repository：`src/db/mysql/repositories/business/team_repo.py`。

### 4.2 设计细则

- `team_id` 格式 `team-{uuid}`，对齐 `kb-{uuid}` 惯例。
- 团队名不做全局唯一（不同 owner 可同名），列表按 joined_time/create_time 排序。
- **解散保护**：`DELETE /api/team/{id}` 前检查是否存在 `visibility='team' AND team_id=? AND deleted=0` 的知识库，有则 409，提示先删除/转出库。
- 软删除沿用 BaseModel `deleted` 位；`team_member` 纯关系表不软删（物理删行）。
- 成员上限建议 500（防误操作/性能兜底），超过拒绝并提示。

## 5. folio-aks-server 改造清单（主战场）

### 5.1 判权核心：KBAccess

新增 `src/service/knowledge/kb_access.py`：

```python
@dataclass
class KBAccess:
    can_read: bool
    can_write: bool
    can_manage: bool

async def resolve_kb_access(session, user_id: str, kb: KnowledgeBase,
                            *, is_admin: bool = False) -> KBAccess: ...
```

判定矩阵（唯一事实源，所有端点过它，不允许各自写条件）：

| visibility | can_read | can_write | can_manage |
|---|---|---|---|
| private | owner | owner | owner |
| team | team member | team member | team owner / KB 创建者 / 平台 admin |
| public | 任何登录用户 | KB 创建者 / 平台 admin | 同 can_write |

实现要点：

- `is_admin` 用 `folio-auth-core` 的 admin 判定（JWT role claim 或 `FOLIO_AUTH_ADMIN_USER_IDS` env 白名单），AKS `.env` 增加 `FOLIO_AUTH_ADMIN_USER_IDS`（JP 参考值 `84852241`）。
- team 成员查询是联合主键点查，单请求一次，量级可忽略；如热路径有顾虑可加进程内 60s TTL 缓存（一期不做）。
- 对外统一 404（存在性不泄露）+ 403（已鉴权但无权限）两种返回，私库越权一律 404。

### 5.2 API 端点改造

#### 5.2.1 知识库 CRUD（`api/routers/knowledge/knowledge_base.py`）

| 端点 | 现状 | 改造 |
|---|---|---|
| `POST /base/create`（:61） | 直接建 | 请求体新增 `visibility`（默认 private）+ `team_id`；校验：team ⇒ 请求者 ∈ 该 team；public ⇒ 过 `PUBLIC_KB_ADMIN_ONLY` 开关 |
| `GET /base/list`（:113） | `get_by_user_id` 只回自己的 | 改三路 union：**自己的 private + 所在 team 的 + 全部 public**；响应 schema 补 `visibility / team_id / team_name / creator`（前端现在连创建者都拿不到）；顶层附 `permissions: {can_create_public: bool}` 供前端显隐创建入口 |
| `GET /base/{kb_id}`（:159）、`PUT`（:181）、`DELETE`（:231） | owner 校验 | read ⇒ can_read；改名 ⇒ can_manage；删除 ⇒ can_manage（级联规则不变：须无文件） |

响应示例（list 单项）：

```json
{
  "knowledge_base_id": "kb-a1b2",
  "knowledge_base_name": "硬件组资料库",
  "knowledge_type": "common_file",
  "description": null,
  "visibility": "team",
  "team_id": "team-x9y8",
  "team_name": "硬件组",
  "creator": "84852241"
}
```

#### 5.2.2 团队 API（新增 `api/routers/team/`，挂 `/api/team`）

放知识库前缀之外（`/api/knowledge/*`）是因为 team 是授权客体而非知识概念，将来 agent/技能侧复用时不必挂在知识库下。

| 端点 | 语义 | 权限 |
|---|---|---|
| `POST /api/team` | 建团队 `{name, description?, member_user_ids?}`，创建者即 owner | 任何登录用户 |
| `GET /api/team/list` | 我相关的团队（own 的 + 加入的），附角色 | 登录 |
| `GET /api/team/{team_id}` | 详情 + 成员列表（user_id + 显示名，显示名由前端用缓存的用户信息补，或后续加批量取名接口） | 本团队成员 |
| `PUT /api/team/{team_id}` | 改名/描述 | owner |
| `DELETE /api/team/{team_id}` | 解散（有库绑定 409） | owner |
| `POST /api/team/{team_id}/members` | 批量加成员 `{user_ids: []}` | owner |
| `DELETE /api/team/{team_id}/members/{user_id}` | 移除成员（不可移 owner） | owner |

JP 的"从部门导入"**不是**这里的专属端点：前端先调 auth 的部门成员 API（§6.1）拿到 user_id 列表，随 `POST /api/team` 的 `member_user_ids` 一次带入。快照语义由此天然成立，AKS 对 OA 无任何感知。

#### 5.2.3 上传 / 索引 / 文件夹 / 文件

全链路把"owner 相等"换成 KBAccess：

- `index.py` upload（:235）/ batch（:352）/ build（:484）：现在 `get_by_id_and_user` 校验归属，改为 can_write。
- `folder.py` / `file.py` 全部端点：team/public 库内文件夹与文件的**查询按 kb 聚合**（用新索引 `idx_kb`），行上的 `user_id` 保留为"上传者"语义（团队库内成员 B 能看到并管理成员 A 传的文件）。
- Repository 新增按 `(knowledge_base_id, file_id)` 取文件的方法（现在只有 `(user_id, file_id)` 联合主键路径），move/delete 对 team 库成员放开。
- `file.py` 的 preview / raw（:247/:314）鉴权从 user 相等改为 can_read（这两端点同时被前端文件查看器用 `?token=` 直连，走 `get_current_user_id_from_token` 通道，改造同样适用）。

#### 5.2.4 检索链路（最深的一处）

原则：**API 入口先判权（can_read），通过后 filter 构造按可见性分流**——

```
private KB → MetadataFilter(user_id=me, knowledge_base_id=X)     # 现状，纵深防御保留
team/public KB → MetadataFilter(knowledge_base_id=X)             # 去掉 user_id（否则必然 0 命中，见 §2.2）
```

| 端点 | 改造 |
|---|---|
| `POST /retrieve`（:88）/ `/retrieve/custom`（:129） | 构造 filter 前逐 kb 判 can_read（不过 → 403）；按可见性决定是否带 user_id |
| `POST /retrieve/single`（:172） | **修 H1**：先解析目标 kb（body 里 knowledge_base_id 必填化或按 document 反查）判 can_read，再按可见性构造 filter |
| chunk 三端点（chunk.py:41/:125/:229） | **修 H2**：chunk → `ChunkSectionDocument` 反查 kb → can_read；弃用的 `_user_id` 参数接回判定 |
| 对话检索工具 `search_knowledge_base` / `grep_chunks` | filter 构造从 `MetadataFilter(user_id=kit.user_id)` 改为"会话 KB 的可见性分流"（会话创建时已校验，运行时一次点查 team_member 即可） |
| 墓碑 `exclude_deleted`（tombstone.py:79-93） | team/public 库改为**按 kb 查待清理 document_id**（成员删文档 = 全团队删除）；private 库维持 `(user_id, kb)` |

字面检索路（`_filter_helper.py`）按 kb/doc/section 走 MySQL 关系表，无 user_id 条件，**结构上不用改**，只需上游传入的 kb 已经过判权。

多 KB 混合 filter（`((user_id==me and kb==A) or (kb==B))`）本期不做：`MetadataFilter` 是 AND 语义且对话工具实际单库（§2.5），列为 §10 遗留项。

#### 5.2.5 会话链路

- `create_session`（session_service.py:82-161）：**修 H3**——对 `knowledge_base_ids` 逐个 can_read 校验（对齐 folder 已有的 `_validate_folder_against_kb` 模式）。
- WS 侧 `get_session(session_id, user_id)` 归属校验不变（chat_service.py:1056-1071）；`ChatRequest.user_id` 来自 session 不可伪造，不变。
- 会话回放 / citations 引用的 chunk 图表端点即 §5.2.4 的 chunk 三端点，修完自然收敛。

### 5.3 SHA256 去重与删除语义（共享底座的收尾）

- 同文档多成员上传：全局 `document_id` 共享向量，`workspace_file_system` 各自记 file 行（现有行为，天然正确）。
- 删除文件：team 库成员删 file 行 + 打墓碑 → 墓碑按 kb 排除 → 全团队检索不到；private 库行为不变。
- 需要评估的既有交互：用户 A 的**个人库**与**团队库**同时引用同一 `document_id`（SHA256 相同）时，团队侧打墓碑**不得**影响个人侧——墓碑键从 `(user_id, kb)` 改为 `(kb, document)` 后天然满足（kb 不同键不同）；反向亦然。
